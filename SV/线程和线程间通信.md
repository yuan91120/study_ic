# 2. 线程管理

- `begin..end`：以顺序方式执行



## **线程启动**

- `fork...join`：

  主线程处于**阻塞**状态，必须等到`fork`块内所有的子线程全部执行完毕，主线程才继续往下进行

- `fork..join_any`：

  主线程处于**阻塞**状态，只要 `fork` 块内**任意一个**子线程执行完毕，主线程就会被唤醒往下走，而其他未完的子线程在后台继续运行。

- `fork..join_none`：主线程**完全不阻塞**。主线程直接往下走，所有的子线程被送入后台等待调度。



## **线程控制语句**

- **`disable fork;`**：**切断当前线程衍生出的所有活跃子线程**。

  通常与 `fork ... join_any` 搭配使用（例如：当“正常传输完毕”或“超时定时器触发”任意一个先发生时，立刻用 `disable fork` 杀掉另一个）。

- **`wait fork;`**：**挂起当前线程，直到所有衍生出的子线程全部执行完毕**。

  通常用来确保后台并发的任务彻底清空后再进入下一个测试阶段。



## **动态线程**：`foreach` 循环中的并发陷阱

如果你在 `foreach` 循环里启动 `fork-join_none` 产生多个线程，必须非常小心**循环变量的局部化**：

```verilog
// ❌ 错误写法：所有线程最终打印出的 i 都是相同的值（循环结束后的最终值）
foreach (data[i]) begin
    fork
        $display(data[i]); 
    join_none
end

// ✅ 正确写法：在循环内部声明局部变量，为每个线程“拍照存根”
foreach (data[i]) begin
    automatic int j = i;
    fork
        $display(data[j]); 
    join_none
end
```



# 3. 线程间通信IPC

当多个线程同时运行时，它们必须互相配合。

三种标准通信工具：

## 事件 (Event) —— 纯粹的时刻同步

用一个线程通知另一个线程“某件事发生了”

- **传统 Verilog 边缘等待 (`@e`)**：对触发的时序要求极度严苛。

  如果线程 A 在时钟 10ns 触发了 `->e`，而线程 B 在 11ns 才执行到 `@e`，那么线程 B 将**永远错过**这次通知，导致死锁。

- **SV 状态等待 (`wait(e.triggered)`)**：安全得多。

  它会检查在当前时间片（Time-slot）内该事件是否被触发过。

  即使触发先发生、等待后发生（在同一时刻内），也能成功捕捉。

- **非阻塞触发 (`->>e`)**：允许延迟触发，可以用来微调事件在时间片中的执行顺序。





## 旗语`Semaphore`：资源排他性访问（互斥锁）

用于管理共享资源（如内存块、唯一的总线接口），防止多线程同时驱动导致信号冲突。

底层：一个原子计数器与一个线程等待队列。

- 概念：基于“水桶与钥匙”。初始化时定义桶里有几把钥匙 `new(N)`。

- **阻塞获取 (`get(n)`)**：

  线程去桶里拿 $n$ 把钥匙，如果钥匙不够，该线程**挂起阻塞**，直到其他线程归还。

- **非阻塞获取 (`try_get(n)`)**：

  有钥匙就拿并返回 1；

  没钥匙不等待，立刻返回 0 并继续执行后续代码（用于实现“顺便看看，不行拉倒”的逻辑）。

- **归还钥匙 (`put(n)`)**：用完必须归还。

```verilog
int timeout = 0;
while(!bus_semaphore.try_get(1)) begin
    #1ns;
    timeout++;
    if(timeout > 100) begin
        `uvm_fatal("TIMEOUT", "抢占总线资源超时！")
    end
end
// 抢占成功，执行总线操作...
bus_semaphore.put(1);
```





## 信箱`mailbox`——带缓冲的数据传输管道

信箱：典型的FIFO（先进先出）队列

- 本质：封装了面向对象特性的线程安全FIFO存储区



- 信箱类型

  - **普通信箱 `mailbox`**：

    内部存储的是 `dynamic` 类型的基类句柄。

    放入（`put`）和取出（`get`）时，仿真器在后台进行隐式的类型转换。

    如果类型不匹配，在运行时（Runtime）才会报出致命错误。

  - **参数化信箱 `mailbox #(Type)`**：

    在编译期（Compile-time）就锁死了类型。

    如果你尝试把一个 `BadPacket` 塞入 `mailbox #(GoodPacket)`，编译器会直接拒绝通过。这是工业界标准的做法。



- 容量分类：

  - **定容信箱** (Bounded Mailbox)：`new(max_size)`。

    当信箱满了，发送端 `put()` 会被**阻塞**。

    这能天然起到“限速”作用，防止 Generator 跑得太快把内存撑爆。

  - **无限信箱** **(Unbounded Mailbox)**：`new()`（不传参）。

    容量无限，发送端永不阻塞。



- 信箱容量窥探

  - `mbx.num()`：返回当前信箱中包含的信息（Transaction）的数量。

  ```verilog
  if (mbx.num() == 0) begin
      $display("信箱是空的，Driver 正在挨饿，赶紧发包！");
  end else if (mbx.num() > 10) begin
      $display("信箱快撑爆了，延迟 100ns 再发...");
  end
  ```

  



- 阻塞方法：会挂起线程
  - 放入数据：`put()`
  - 移出数据：`get()`
  - 看而不取：`peek()`



- 非阻塞方法：立刻返回状态
  - 放入数据：**`try_put(message);`** (成功返回1，满返回0)
  - 移出数据：**`try_get(message);`** (成功返回1，空返回0)
  - 看而不取：**`try_peek(message);`** (不移除数据，仅查看)



- 类型安全问题：

  - 默认的 `mailbox` 是可以塞入任何类型数据的（因为其内部存储的是全局句柄 `invalid` 指针）。

    如果误把 `Instruction` 塞进了本该装 `Packet` 的信箱，运行时会报错。

  - 推荐使用**参数化信箱 (Parameterized Mailbox)** 来做编译期类型检查：`mailbox #(Packet) mbx;`。



# 4. 总结

事件`event`：

- 使用场景：**纯时序握手**（A跳变了，通知B）
- 核心方法：`->`,  `wait(e.triggered)`



旗语`semaphore`：

- 使用场景：**硬件资源互斥**（多驱动抢占单一接口）
- 核心方法：`try_get()`, `put()`



信箱`mailbox #(T)` ：

- 使用场景：**数据传输兼顾步调控制**（组件间传包）
- 核心方法：`put()`, `get()`
